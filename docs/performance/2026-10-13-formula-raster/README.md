# 公式白底增量合成：减少重负载长停顿

2026-10-13，继续第一轮渲染长尾检查；不另计为里程碑第四轮。结论：保留增量合成以减少公式编辑压力场景的长帧，不把本组结果计作 CPU 或节能收益。

## 机制与画质

原公式窗口在每次抬笔后清空并回放全部已完成笔迹。候选只追加引用与顺序未改变的笔迹；删除、清空、恢复草稿、同 ID 几何修改、重排、画布替换和尺寸变化仍完整回放。抬笔立即更新、活动笔迹、960×320/640 白底、压感、透明叠加、识别裁剪和保存策略保持一致。

冻结 A/B 的完整源快照只有 `src/FormulaDialog.tsx` 不同：A 在每次脏画布合成前重置增量状态；双方均包含相同的 `FormulaInk` 类、不可变笔迹数组与其它修改。逐个实际运行文件的哈希包含在原始报告中。

质量证据：浏览器 8 项检查通过，含 CPU/GPU 与完整回放严格逐通道零差异、草稿/源码/光标恢复、多行识别的模拟服务、取消及插入位置；实际冻结 B 的 Electron 另外通过 9 项画布与保存向量检查，逐通道零差异。后者包含 20 次追加、取消、重开、640 高度、下半区追加、删除及清空恢复。未调用真实识别模型，未测物理笔延迟，未注入物理 GPU 重置。

## 完整流程：三组交错 A/B

同一固定混合 PDF、3000 笔迹、当前高清目标、1440×960 内容窗口；包括导入、书写、擦除、撤销、连续滚动、双页缩放、日夜切换、公式编辑/保存、空闲尾部和隐藏/恢复。每阶段等待已跟踪任务完成，包含恢复后的工作。六轮没有不完整 CPU 区间。

公式压力操作在一个脚本任务中分发 200 笔，再聚焦源码并移动光标 50 次。这是积压压力场景，不代表真实用户连续输入速度。其它阶段完整计入，当前保留依据是明显缩短压力场景的长停顿及画质不变，而非 CPU 改善。三次重复不构成统计显著性证明。

## 初始化异常与独立 trace

最初六轮中 B3 的 setup 出现同 PID/creationTime 累计 CPU 倒退。两项初始整数刻度随后切换到高精度计数，不能把倒退解释为进程重启，也不夹取为零。原组六轮、完整日志与审计保存在 `diagnostics/initial-*`；整组不作正式比较。

新的工具先完成已跟踪的启动工作，再以 200 ms 间隔等待连续两对稳定进程计数，最多 26 次读取；所有初始化读数在 `counterWarmup` 中保留，之后每个统计区间仍须完整。启动不属于本次交互流程统计，正式窗口从导入前空闲开始。六轮正式结果均通过；启动耗时未作为改进。

另外保留了第一轮保存优化的两份完整诊断 trace、原始报告、分析脚本与哈希。它们使用旧冻结构建，不能混入本组指标。最大 RAF 空隙跨过源码聚焦、悬浮键盘显示和前半段光标移动；不能全部归因于草稿保存或同步笔迹分发。trace 没有 `toplevel` 根任务类别，嵌套时间不能相加，也不足以证明最长空隙内主线程完全空闲。完整诊断保留为后续键盘/合成器检查的输入。
