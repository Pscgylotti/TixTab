# PDF.js / PDFium WASM raster comparison — 2026-10-15

Core Ultra 5 238V, Windows x64, headless Edge. PDF.js 5.4.624; `@embedpdf/pdfium` 2.15.1. This measures the experimental hybrid integration, with PDF.js document metadata still present in PDFium mode. It is not a PDFium-only application measurement.

Each input/engine runs once in a fresh browser, sequentially, at identical output dimensions. No repeated-run averages. Scale is 1.5 PDF coordinate units, capped at four million pixels per page. Page raster caches are bypassed; each output canvas is released and `page.cleanup()` runs after its page. Worker rendering, bitmap transfer and final canvas presentation are included. First raster includes PDFium's lazy engine setup and document import; common PDF.js document parsing is timed separately in the raw report. Later-page medians refer to different pages, not repeated trials of one page. No battery or power measurements were made.

Inputs:

- *Optimal transport old and new, Part 1*, the supplied 113,703,710-byte scanned PDF, pages 40–100 inclusive (61 pages). Output is about 620 × 973 pixels per page.
- Reproducible 12-page fixture, each page with 55 text lines and 800 vector segments, 900 × 1200 output pixels.

| Input / engine | First raster ms | Later-page median ms | Total raster ms | Sequential pages/s | Sampled max private MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| Scanned book / PDF.js | 62.0 | 37.0 | 2463.6 | 24.8 | 771.0 |
| Scanned book / PDFium | 376.5 | 18.5 | 1553.7 | 39.3 | 1161.1 |
| Text/vector / PDF.js | 34.3 | 12.9 | 191.9 | 62.5 | 477.7 |
| Text/vector / PDFium | 103.0 | 11.0 | 232.9 | 51.5 | 537.9 |

In this pass PDFium's scanned-page median is half PDF.js's, and its total raster time is 36.9% lower even including engine initialization. For the short text/vector input, later pages are 14.7% faster by median but the total is 21.4% longer because initialization dominates. Neither result establishes a universal engine ranking, especially for higher zoom, transparency, masks, or more complex documents.

Memory is summed across this browser's process tree at the first/middle/final page, not a continuous true peak or Electron application total. It includes the application shell, source bytes, PDF.js metadata, the PDFium WASM instance and browser/allocator behavior. The PDFium scanned case sampled about 390 MiB more private memory. Immediate close is not followed by forced garbage collection, so retained process memory cannot be classified as a leak from this report alone.

The updated implementation keeps one initialized engine resident. After document closure, PDFium reports **one Worker, zero native documents, zero sessions and zero pending requests**. Its reusable linear-memory high-water buffer remains 132.25 MiB for the scanned input and 17.75 MiB for the vector fixture. Separate repeated-close and simultaneous-document tests verify handle release and engine reuse.

Decision: keep PDF.js as the default during staged migration. PDFium is promising for steady scanned-page rendering, but the current double-engine architecture costs memory. Remove duplicate document/text/image infrastructure in validated stages before claiming a memory improvement.

Reproduce with a development server at port 5173 and `node scripts/benchmark-pdf-engines.mjs`; `--pdf`, `--first`, `--last`, `--out`, and `--base` override inputs and paths. Run engines sequentially without other builds or tests. [Raw report and source hashes](render-20261015.json).
