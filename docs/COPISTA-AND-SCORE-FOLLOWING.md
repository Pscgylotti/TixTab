# Copista 28M and microphone score following

In Extra tools → Music recognition, select **Copista 28M**, prepare the component once, and choose the current page, all pages, or a page range. Results use the existing score player, MIDI correction, MIDI/MusicXML export and project persistence.

The adapter pins [KobiMusic copisteria](https://github.com/kobimusic/copisteria) 1.3.4 at `c685f280914d91a694494588d9f6a376d7917eba` and [Copista 28M](https://huggingface.co/kobimusic/copista-28m) weights at `44464d11234a22ba23634ec8eb1e31e3b012021a`. The 28M detector and shared evidence model run locally on the CPU. Source and weight downloads have size and SHA-256 verification; their Apache-2.0 LICENSE and NOTICE files are retained. Copisteria itself is unmodified; TixTab's adapter attaches emitted MusicXML note IDs to detector coordinates, preserving location through chord, voice and tied-note ordering.

The `copista` runtime profile installs PyTorch, torchvision and scipy into the existing managed **homr Python 3.12 environment**, without creating another virtual environment. Model/source downloads total about 119 MiB; Python dependencies are additional. One owned subprocess handles one page at a time; cancellation stops its process tree. Temporary source images, detector features and generated files are removed on completion or cancellation, and exiting the subprocess releases the model heap. Only MusicXML and normalized score geometry enter the project.

Component setup includes the repository's `models/yolo_v7_taxonomy.json`, instrument and staff-link metadata, and imports the installed pipeline before marking it ready. Older installations with a ready marker but missing metadata are repaired automatically from the verified source archive. Both validation and recognition explicitly use Python UTF-8 mode: isolated mode ignores the `PYTHONUTF8` environment variable, and the upstream instrument metadata contains non-ASCII names. Validation must use the managed installation directory, not an independently extracted development checkout.

## Playback sound source

The player's **Sound source / 音源** selector connects to local Windows MIDI output devices through WinMM. **Automatic** prefers the Windows General MIDI software synthesizer (usually **Microsoft GS Wavetable Synth**) and otherwise uses the built-in oscillator synth. It never automatically selects a hardware/virtual MIDI bridge. Select a different exposed MIDI port explicitly to play through an external synthesizer or a virtual port connected to a software instrument. A bridge alone does not produce audio; sound quality and General MIDI program support depend on the connected instrument. No additional Python environment or sound bank download is required for the Windows system synthesizer.

The chosen output is remembered. Refresh discovers newly connected devices; unavailable selections produce a visible playback error rather than silently sending to a different port. Instrument and volume controls affect the selected output. MIDI scheduling runs in an isolated worker with a bounded score payload. Pause, seek, output changes, player close, document changes and renderer shutdown stop playback and reset/close the MIDI device. Idle workers are released after 30 seconds. The existing score cursor, automatic page turns and microphone following continue to use the same timeline.

## Microphone following

The desktop player defaults to **Matchmaker · Global positioning (HMM)**. Click **Prepare Matchmaker components** once, then enable **Follow audio** with the microphone button. This reuses the existing managed homr/Copista Python 3.12 environment, plus a verified local FluidSynth library and GeneralUser GS reference SoundFont (about 34 MiB; Python dependencies are additional). It does not use the selected Windows MIDI output for analysis. No extra virtual environment is created.

The pinned upstream [Matchmaker](https://github.com/pymatchmaker/matchmaker) 0.4.0 audio Outer-product HMM maintains hypotheses across all score note onsets, including backward and forward jumps. Unlike its default registry configuration (jump probability zero), the adapter enables global transitions. Recognized MIDI pitches, onset beats and durations form the score states. Piano-key spectral templates are generated locally from the verified bank using the same causal constant-Q extractor as microphone audio. This is an audio-to-score follower, not live MIDI input. Templates cover A0–C8; unsupported instruments, pitches outside that range, OMR errors, pedal/reverb and microphone noise can reduce accuracy.

The adapter reuses upstream `AudioOuterProductHMM.forward_step` and its emission calculation. It initializes the sparse transition diagonals directly, avoiding the upstream constructor's dense N×N matrix and implicit SoundFont synthesis/download. Storage grows linearly with score onsets. A separate local HMM hypothesis keeps tracking the committed passage while the global HMM searches the full score. Distant relocation requires bounded subsequence verification over up to 32 feature frames (about 2.56 seconds of sounding music), several changing note onsets, a margin over competing passages, and consecutive consistent results. Nearby sequence matches also repair a stalled local tracker. Identical repeated passages prefer the established location; a held chord alone cannot cause a cross-score jump. Cursor positions are note/chord onsets, not interpolated metronome positions. Manual seeking supplies a position prior while retaining global alternatives.

Silence holds both the displayed position and the candidate distribution; after 300 ms, hypotheses are retained in pause states. On resumption, the previous distribution is retained with some probability reopened across the full score, permitting either continuation or a restart elsewhere. Silent audio does not advance wall-clock playback. This conservative behavior also holds at written rests: a silent rest and an unplanned pause cannot be reliably distinguished from microphone silence alone. Causal analysis windows are pitch-dependent (up to 512 ms for bass), so capture packet duration is not a promise of end-to-end latency.

**Matchmaker · OLTW** remains selectable for local continuous alignment. It synthesizes recognized MIDI notes into a full reference feature sequence and uses Log Spectral Energy plus Arzt online time warping. It starts from the selected position, with a limited same-tempo recovery search; it is not the global positioning mode. Features update every 20 ms with a 64 ms window. AudioWorklet captures continuous mono audio at 16 kHz in timestamped 40 ms packets for both native modes.

**Built-in CQT (compatibility)** retains the earlier browser implementation: at least five seconds of input, constant-Q pitch features and subsequence DTW over up to eight seconds of recent features. It remains available when the desktop runtime is unavailable. Neither algorithm fixes inaccurate note-to-page geometry from OMR.

Following uses the same page cursor and navigation as playback, including single-page, continuous, dual-page and presentation views. Disabling following, closing the player, hiding the app or changing the score immediately stops microphone tracks and clears queued PCM and live analysis history. Raw audio is neither saved nor uploaded. Matchmaker keeps at most four queued audio packets plus one in flight and drops older audio rather than accumulating delay. The HMM retains an 8,192-sample ring, fixed pitch kernels, linear score probabilities/templates, and at most 32 feature-distance frames for phrase verification. The OLTW mode caps its recovery history at 200 frames and prunes unused upstream performance history. References are limited to one hour and 100,000 notes. The CQT compatibility worker retains its existing 80-frame history and 30,000-frame reference limits.

Both Matchmaker modes keep the most recently stopped reference warm for the configured **model idle timeout** (default 1,800 seconds). The process waits on input while parked; it does not capture or analyze audio. Reopening the same score sends only a SHA-256 content key and starting position, reusing prepared templates/features and the existing process. A cache miss uploads notes once. MIDI pitch, onset, duration, mute, tempo, instrument or method changes invalidate the key; backend/runtime/model-file changes also invalidate the native reference. Moving the cursor does not. Changing tempo or instrument while following stops capture so the next start builds the appropriate reference. No more than one idle reference is kept across windows, with a conservative 64 MiB retained numeric-buffer limit (separate from Python's baseline heap). Oversized references are released on stop. Idle expiry, replacement, renderer loss and application exit terminate the process and remove its temporary configuration/DLL directory; references do not persist across application restarts.

With the complete LILI score on this machine, cold native preparation took 3,540 ms (global HMM) and 4,350 ms (OLTW); warm reuse took 0.84 ms and 0.83 ms respectively. The checks verified one subprocess per mode, no repeated preparation events, reset audio timestamps/epochs, and temporary-directory cleanup on hard close. These timings cover the main-process reference operation, excluding renderer hashing, microphone permissions/startup and capture latency.

The Windows CPython 3.12 wheel is built from unmodified upstream commit `eacec8128e80fc6de980ac1371f6368176633b38`. Source and binary checksums plus build tools are recorded in `backend/wheels/matchmaker-build.json`; `node scripts/build-matchmaker-wheel.mjs <existing-python.exe>` rebuilds into `.cache`. Installation checks the wheel hash and does not require the user's machine to have a C++ compiler. License metadata is retained in the wheel and downloaded sound assets. The adapter disables Partitura's unused optional FluidSynth integration during import to prevent its implicit legacy FTP SoundFont download; TixTab supplies the verified bank itself.

On this development machine, a deterministic synthetic phrase at 30% slower tempo, with a different piano preset and small added noise, produced median alignment error around 98 ms and p95 around 207 ms. Processing took around 0.27 ms per 40 ms audio packet, excluding capture/IPC, reference preparation and UI updates. This is a synthetic integration check, not a microphone benchmark or a guarantee for real playing.

Those timing figures describe OLTW from a known starting point. HMM acquisition/relocation now deliberately waits for phrase evidence; the earlier frame-only HMM timing measurements no longer describe this behavior. `backend/test_matchmaker_follow.py` checks arbitrary starts, genuine backward jumps, repeated-phrase ambiguity, noise, stale sessions, pause holding, a held distant chord, warm-reference reset and a 10,000-onset score with under 6 MiB of HMM array storage. Run it in the existing managed runtime with the verified test assets.

The user's six-page Copista LILI project (1,905 notes) was tested with the 131-second audio from `[Deemo] LILI piano` (`XmyZ5GfB0pc`). Frame-only HMM produced 52 cursor discontinuities larger than eight beats; the local/phrase-verified version produced zero, visited all six pages and reached the final passage. The same project's synthetic rendition went from 19 such jumps to zero. This checks discontinuities, not per-note ground-truth accuracy or room-microphone latency. The optional regression accepts `TIXTAB_FOLLOW_TEST_PROJECT` and `TIXTAB_FOLLOW_TEST_PCM` (mono 16 kHz float32 PCM); copyrighted input files are not bundled or downloaded by tests.

## Verification

- Copista recognizes a real test score locally and produces mapped notes; test its page/row placement, seeking, MIDI correction and project reload on your own scores.
- Check recognition cancellation and repeat it on several pages; no `document-job-*` directories should remain after completion.
- Enable microphone following, play a phrase, change pace and pass a page boundary in each view. Check silence does not turn pages and manual seeking restarts acquisition.
- In global HMM mode, start several pages from the selected position, pause and resume, then restart an earlier passage. Identical repeated music should not select a distant copy until later notes distinguish it.
- Turn following off, close the player and switch documents; the microphone indicator and live analysis should stop. Reopen the same score: reference preparation should be skipped. Edit a note: the next start must rebuild. Confirm the parked process exits after the configured idle timeout or renderer shutdown.
